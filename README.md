# 世界觀架構工作台 — WorldBuilder Canvas

> 改這個專案之前請先看 [`NOTES.md`](NOTES.md)：那裡寫了踩過的坑、不能退回去的規則，以及還沒做完的事。

給小說、劇本、TRPG 用的世界觀整理工具。左邊是資料夾式的文檔目錄，右邊可以在白板上把角色、勢力、地點拉出來連線，標註彼此的關係。

線上版：https://evonne93327-create.github.io/world_2/

---

## 功能

**文檔**
- 多世界觀，各自獨立的資料夾樹狀目錄；新增世界觀時會附一篇空白文檔，建好就能直接寫
- 內文打 `# 第一章 ⋯` 會自動生成章節快速跳轉
- 內文打 `#帝國軍方` 這類 hashtag 會自動抽取、套色，可依標籤篩選與跳轉
- 每篇文檔獨立的復原／取消復原紀錄（連按不會讓畫面跳來跳去）
- 插入圖片、點縮圖可全螢幕檢視、字數統計
- 垃圾桶（可復原），所有世界觀共用、照世界觀分組標示；刪掉的世界觀可以**整個復原**（含白板）
- 目錄樹可拖曳搬移文檔與資料夾，**手機上也可以**（按住一下下再拖）
- 「移動」選單的目的地照世界觀分組列出；搬到別的世界觀時可以選**移動**或**複製一份**過去
  （資料夾會整棵子樹一起搬／複製）
- 每個世界觀可以寫一句話簡介（顯示在目錄的搜尋欄上方，新增世界觀時就可以一起填）
- 輸入名稱時預設文字是反藍的，直接打字就取代
- 世界觀清單：一次看完每個世界觀的名稱、簡介、文件數與最後更新時間
  （手機從底部那一列往上滑，電腦點上方的世界觀徽章）

**白板**
- 把文檔投射成節點，拖曳擺位、縮放平移
- **批量投射**：一次勾選多篇（勾資料夾＝底下全部），排成網格放在既有節點下方，不會疊在一起
- 節點之間拉關係線，可設定文字、顏色、線條樣式與箭頭方向
- 同一對節點之間的多條線會自動對稱展開，不會互相交疊或交叉

**匯入匯出**
- 匯出：HTML（單篇／批量）、TXT、整包資料庫 JSON 備份
- 匯入：JSON、TXT、HTML

**雲端同步**（選用）
- 支援 **Supabase** 或 **Google 雲端硬碟**，在面板上切換
- 修改後自動上傳，換裝置登入同一個帳號就能取得同一份資料
- **三個時機都會自動對帳**：切回前景、在 app 裡換文檔／切白板／回到目錄，
  以及開著沒動時每隔幾分鐘自己掃一次
- **衝突的粒度是「一篇文檔」**：在平板改第 1 篇、手機改第 2 篇，兩篇都會留著；
  只有同一篇兩邊都改才會停下來問，而且會告訴你是哪幾篇
- 不設定的話，資料就只留在這台瀏覽器裡，功能完全不受影響

**手機與平板**
- 軟體鍵盤升起時，版面會縮到看得見的範圍，浮動按鈕頂到鍵盤正上方
- 游標永遠留在鍵盤上方，不會被鍵盤蓋住（見下方的設計決定）
- 從畫面左緣往右滑可以開啟目錄欄
- 目錄裡**按住一列約 0.3 秒**（那一列會浮起來）**再移動手指**就是拖曳搬移，
  右鍵選單不會跑出來；HTML5 的拖放在觸控裝置上根本不會觸發，所以另外走一套。
  拖到側欄邊緣會自動捲動
- 從底部的世界觀那一列**往上滑**可以拉出世界觀清單

**可安裝、可離線**
- 是一個 PWA，可以裝到手機主畫面或電腦上，開起來沒有瀏覽器網址列
- 離線也能開啟與編輯；資料本來就存在本機，連線恢復後才同步
- 設定裡的「版本」點一下會主動去問伺服器有沒有新版，有就直接讓你重新整理

## 本機執行

沒有安裝步驟，也沒有打包流程。用任何靜態伺服器把資料夾開起來即可：

```bash
python3 -m http.server 8000
# 然後打開 http://localhost:8000
```

> 直接用 `file://` 開 `index.html` 也能顯示，但雲端同步與離線安裝都需要正常的網域來源（https 或 localhost）才能運作。

## 測試

```bash
node --test          # 200 項
```

（注意：不要寫 `node --test tests/`，Node 22 會去 `require` 那個目錄。）

不需要 `npm install`，也不需要瀏覽器——專案刻意維持零依賴，測試也跟著這個
取捨走。`tests/helpers/load-app.js` 用 Node 內建的 `node:vm` 把瀏覽器端的
js 載進沙箱，補上幾個 DOM 空殼，就能直接拿裡面的純函式來測。

測的是這幾類東西：

- **純函式**（`tests/pure.test.js`）：標籤抽取、字數計算、TXT 解析、
  HTML 跳脫、圖片來源白名單、匯入資料的驗證，以及鍵盤那幾條算式。
- **白板連線的幾何不變條件**（`tests/edge-geometry.test.js`）：出發角度必須
  隨 spread 單調變化。這個專案踩過「出發點與彎曲分開算會讓線在中段交叉」
  的坑（見下方的設計決定），這組測試就是把那件事釘住——誰把它拆回兩套
  算法，這裡就會紅。
- **離線清單的一致性**（`tests/shell-manifest.test.js`）：`sw.js` 的 `SHELL`
  跟 `index.html` 實際載入的檔案必須對得上。這兩份清單是手動維護的，
  加了新檔案卻忘記補進去的話，離線時會無聲少一塊功能。
- **軟體鍵盤的規則**（`tests/kb-vars.test.js`）：JS 寫進去的 `--kb-*` 與
  CSS 用到的要對得上、`.kb-*` 的 class 兩邊要對得上，以及幾條**不准再犯**
  的規則（補捲不可以有動畫、不可以用「後面有沒有換行」判斷最後一行）。
- **HTML 與 JS 之間的接線**（`tests/wiring.test.js`）：`onclick="foo()"` 要有
  對應的函式、`getElementById` 抓的 id 要真的存在。
- **逐篇三方合併**（`tests/sync-merge.test.js`）與**對帳的時機**
  （`tests/sync.test.js`）：全專案最危險的一段，測得最細。
- **目錄的搬移與拖曳**（`tests/directory.test.js`）：搬移的規則只有一份
  （拖放與「移動」彈窗共用）、資料夾不可以搬進自己的子孫、觸控拖曳每一列
  都有接上、拖曳的幽靈不可以吃到點擊。
- **編輯器的復原、圖片檢視與世界觀簡介**（`tests/editor.test.js`）：
  復原時捲動位置要還原、補捲不可以有動畫、圖片放大前要過白名單。
- **手勢之間搶事件**（`tests/gestures.test.js`）：左緣滑動接手後會攔掉後續
  事件，所有長按的「取消」都要聽在攔不到的地方，否則滑一下就會長出便利貼、
  跳出選單。

這幾類有一個共同點：**它們擋的都是「不會報錯」的失敗**。`var()` 取不到值、
class 沒人吃、onclick 打錯字、離線少一個檔案——瀏覽器全都不會吭聲，只會安靜
地少做一件事。這種東西用眼睛看很難發現，用比對很容易擋掉。

慣例：**每加一條測試，都要先把程式改壞、確認它真的會紅**。綠燈不代表測到了，
這份測試自己就有好幾條第一次寫出來是「怎麼改都綠」的，原因寫在各自的註解裡。

網站本身就是 PWA，不需要下載任何東西：

## 雲端同步設定

同步是選用的，不設定不影響任何其他功能。資料本來就存在瀏覽器的 localStorage，同步只是多推一份到雲端。

點左側的 **☁️** 開啟設定面板，選一種後端：

### Supabase

1. 到 [supabase.com](https://supabase.com) 建立免費專案
2. 進 **SQL Editor**，把 [`supabase/schema.sql`](supabase/schema.sql) 整份貼上執行
3. 到 **Settings → API** 複製 **Project URL** 與 **anon public** key
4. 貼進同步面板 → 建立帳號 → 完成

> 只需要 `anon` 那把金鑰，它設計上就可以公開；**`service_role` 那把絕對不要放進前端**，它會繞過所有權限檢查。`anon` key 的安全性由資料表的 Row Level Security 保證，規則寫在 `schema.sql` 裡：每個帳號只能存取自己那一列。

### Google 雲端硬碟

資料會存成你雲端硬碟裡的 `worldbuilder_data.json`，看得到也能自己下載。

設定步驟見 [`google-drive-setup.md`](google-drive-setup.md)，大約 10 分鐘，需要到 Google Cloud Console 申請一組 OAuth 用戶端 ID。

> 權限範圍只用 `drive.file`，屬於非敏感範圍，不需要送 Google 審查；它也代表這個 app **只碰得到自己建立的那個檔案**，看不到你雲端硬碟裡的其他東西。

## 幾個值得知道的設計決定

### 白板連線：先畫完整曲線再裁掉

線的起點不是另外挑一個邊框位置算出來的，而是**曲線與節點邊框的交點**。

每條線從 A 節點中心畫一條三次貝茲到 B 節點中心，兩端各往同一側轉開一個角度（角度大小由這條線在同組中的序位決定），再把落在節點內部的部分裁掉。

這樣彎得越開的線，交點自然落在越外側，**出發順序必定跟彎曲順序一致，結構上不可能交叉**。早期版本把「出發點」和「彎曲」當成兩件事分開算，兩者的排列方向在節點斜向擺放時會相反，線就一定會在中段互相穿越——拿掉彎曲變直線、加回彎曲又交叉，怎麼調參數都治不好。

用「出發角度」而不是「中段彎曲量」當控制參數也是必要的：彎曲量必須設上限（否則長線會鼓得很誇張），但控制桿長度隨節點距離成長，一旦設了上限，節點拉遠時所有線離開節點的方向就會趨近平行，端點擠成一點。

### 雲端同步：寧可停下來問，也不默默覆蓋

整包資料存成雲端的一筆記錄。這跟現有架構完全吻合（`saveData()` 本來就是唯一出口），代價是衝突沒辦法逐篇文件合併，只能整包擇一。

因此原則是絕不自動猜：

- 版本號由**伺服器端**維護（Supabase 用資料庫 trigger）。不採用用戶端時間戳——裝置時鐘可能是錯的，拿它判斷會誤判衝突。
- Supabase 的推送是**條件式更新**（版本相符才會寫入），而不是「先讀再寫」，避免競態。Google Drive 沒有這種機制，只能寫入前先讀一次比對，保證較弱，程式碼中已註明。
- 一旦偵測到別處改過，跳出對話框讓使用者選雲端、選本機，或先存一份檔案再決定。
- 「本機有未上傳變更」的旗標存在 localStorage。只放記憶體的話，使用者改完直接關掉分頁，下次開啟就不知道本機是新的，會默默採用雲端而弄丟這次的修改。

兩種後端各自保存自己的設定，切換不會弄丟任何一邊；但資料不會跟著搬移，切換時若本機還有未上傳的修改會先警告。

**衝突的粒度是一篇文檔，不是整包。** 雲端存的是整包資料的一筆記錄，所以「兩邊
都有改」原本只能整包二選一——但那多半是「這台改第 1 篇、那台改第 2 篇」，挑哪
邊都會丟掉另一台的那一篇。現在會先做三方合併，只有**同一篇兩邊都改**才停下來問。

祖先（上次同步的狀態）**只存每一項的雜湊，不存內容**：這個 app 的圖片是 base64
存在文檔裡的，存整包快照會讓 localStorage 的佔用直接翻倍。而三方合併其實只需要
回答「這一邊跟祖先一不一樣」，不需要祖先的內容。

刪除不需要墓碑——祖先裡有、這一邊沒有就是這邊刪了；垃圾桶也走同一套合併，所以
「從垃圾桶還原」自然就對。沒有祖先時（第一次同步、剛換後端）會退回整包二選一，
因為那時分不出是誰改的，硬合併等於瞎猜。

**對帳的時機不只開啟那一次。** 裝成 app 的人常常是「切到後台、在另一台改東西、
再切回來」，而那個過程不會重新載入頁面——只在啟動時對帳的話，切回來看到的還是
離開前的資料。

所以一共四個時機，走的都是**同一套判斷**（兩邊各寫一套的話，遲早有一邊比較
寬鬆，而在這裡「比較寬鬆」的意思就是某個情況下會安靜地覆蓋掉一邊的資料）：

| 時機 | 靠什麼觸發 |
|---|---|
| 開啟 app | `initSync()` |
| 切回前景 | `visibilitychange` 與 `pageshow`（iOS 從 bfcache 還原只保證發後者） |
| 在 app 裡換地方看 | 換文檔、切文檔／白板、打開目錄欄 |
| 開著沒動 | 每隔幾分鐘自己掃一次，只在看得見的時候 |

最後那個的間隔明顯比「重試上傳」長：重試只有在本機真的有東西要推時才動作，
成本是零；定期對帳每次都是一發真的 API 請求，太頻繁會吃掉 Supabase 的免費額度
與 Drive 的配額。藏在背景時不掃——看不到的東西不需要更新，而且 iOS 本來就會把
背景分頁的計時器凍結。

兩個細節：對帳前要先把還在 debounce 裡的編輯存起來（內文是改完 400ms 才存檔的，
而「本機有未上傳變更」是存檔時才標記的——少了這一步，剛打完就切走、回來時那些字
會被當成不存在）；以及兩次對帳之間有最短間隔，因為 iOS 的 `visibilitychange`
有時會連發。

### 軟體鍵盤：iOS 的 `dvh` 不扣鍵盤

iOS 的 `100dvh` **只扣瀏覽器自己的網址列，不扣軟體鍵盤**——鍵盤是「蓋」在畫面
上的，版面完全不知道。（`interactive-widget=resizes-content` 只有 Chrome／
Android 認得，iOS 直接忽略。）所以鍵盤的高度只能從 `visualViewport` 算，而那裡
有好幾個不同的量，混用就會出事。細節在 [`NOTES.md`](NOTES.md) 的 3c～3d，這裡
只講三個結論：

**一、`body` 的上緣跟下緣要分開顧。** iOS 為了讓游標露出來會把整個版面視窗往上
推，只把高度縮到「看得見的底」的話，下緣是對了，上緣連同最上面的工具列一起被推
出畫面。所以外框給「版面頂端→看得見的底端」，再補一段 `padding-top` 把內容讓
回來。

**二、游標要能被捲到鍵盤上方，底下就得有東西可以捲。** 但要留多少，取決於容器
有沒有先縮掉：鍵盤升起之後主結構已經縮成可視高度，容器少了一個鍵盤的高度而內容
沒變，**可捲範圍自己就多出一個鍵盤的高度**——那時只需要再留「浮動按鈕那一排 ＋
兩行」。真正要自己補的只有「聚焦了、鍵盤還沒升起」那一小段。

這裡算錯過一次（拿縮之前的高度去算，多留了一整個鍵盤的高度），Android 使用者
每次捲到底都會撞進那片空白。Android 的版面本來就會自己 resize，那塊空間一開始
就不需要。

**三、聚焦時那一下補捲不能有動畫。** 這是硬限制，不是還沒做——它在跟 iOS 搶時
間，只要鍵盤升起的那一刻游標已經在安全位置，iOS 就沒有理由去推版面。試過瀏覽器
內建的 `behavior: smooth`（300~500ms）與自己寫的 160ms 動畫，兩種都輸。程式裡有
negative 測試擋著，因為這個錯誤的症狀（工具列被吃掉）看起來像完全無關的另一個
bug，要好幾輪之後才會被發現。

還有一個 **🩺 鍵盤診斷**：打開後畫面左上角會即時顯示 `visualViewport` 的實際
數字、那幾個 CSS 變數的值、工具列與浮動按鈕的位置。這個環境裝不起 WebKit，
iOS 上到底發生什麼事只有實機知道——有這塊面板就不必用猜的。

它平常是藏起來的（只有回報鍵盤問題時才用得到）：**長按或右鍵點設定裡的
「版本」那一列**就會跳出開關。

### Service worker：網路優先，不是快取優先

一般 PWA 教學都是快取優先（先給快取、背景再更新），但這個 app 是持續部署到 GitHub Pages 的，快取優先會讓人被鎖在舊版程式碼裡——而且很難自救，因為連強制重新整理都是由 service worker 回應，根本沒碰到網路。

所以這裡刻意反過來：**先走網路，失敗才回退快取**。連線正常時不會變快，但「更新一定拿得到」。對這個 app 來說這個取捨很划算，因為資料本來就在 localStorage，網路只負責抓靜態檔案。

另外兩點：跨網域請求（Supabase、Google API）一律放行不快取，否則同步會讀到過期回應；預先快取是逐檔加入而不是 `addAll`，因為 `addAll` 只要有一個檔案失敗就整批拒絕，會導致 service worker 裝不起來、離線功能無聲消失。

還有一個不明顯的陷阱：`skipWaiting()` + `clients.claim()` 會讓新的 worker **立刻
接管已經開著的那一頁**。於是設定裡顯示的版本（問 worker 拿的）是新的，但這一頁的
CSS 與 JS 還是載入當下那一版——使用者看到新版號、以為在跑新程式碼，回報「你改了
還是一樣」。這真的發生過，白查了一輪。所以 worker 一接管就會把這一頁標記成
「跑著舊程式碼」，而且那個判斷排在所有其他分支**之前**（兩邊版號這時是一致的，
排在後面就永遠輪不到它）。
